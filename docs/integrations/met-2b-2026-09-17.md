### The total is a range, and it may have crossed the ceiling

Pass 2 was stopped by this session when it reached the object count its budget
allowed, and it is the run that prints its own ledger, so its exact request count
was lost with the process. What is certain: it wrote **803** hydrations and made
**5** searches, it never reached its own 870 ceiling (it would have stopped and
written the manifest), and at most **43** of its requests can have failed —
2,290 ids minus the 2,247 in the cache. So the session spent between **3,482 and
3,525** Met requests against D14's **3,500**, and the upper half of that range is
over the ceiling.

That is a ledger defect, not a budget defect: the builder should write its
running totals as it goes rather than only at the end. `--from-cache` now exists
so a stopped run can be finished without spending anything, which removes the
reason to kill the process in the first place.

### What pass 1 measured, and why there is a pass 2

Pass 1 was capped at 2,600 requests and spent them all without finishing:

| Pass 1 | |
|---|---:|
| candidate ids from the search | 2,290 |
| objects hydrated | 1,444 |
| `403` refusals | 1,149 |
| retries spent on those refusals | 828 |
| objects abandoned after 3 attempts | 323 |
| public-domain objects kept | 1,184 |

**This is the P0 probe's 403 finding reproduced at length.** 2a saw no refusals
in two 26-request runs and the 16:46 audit failed to reproduce them in a
20-request burst; a 2,600-request run at 1 req/s was refused **44% of the time**.
The Met throttles on sustained volume, not only on burst rate. An in-run retry
costs a request immediately, so pass 1 spent 828 requests re-asking for objects
instead of asking for new ones.

Pass 2 therefore runs at **3 s/request with one attempt per object** and resumes
from the hydration cache, so nothing already fetched is paid for twice. Measured
at that pace, refusals essentially stop (25 of 26 requests answered in the first
80 seconds). `--max-attempts` exists because of this measurement.

## The sitelink threshold, measured

Whole-graph sitelink counts do time out, and half-open bands do not fix it: a
`FILTER(?sitelinks >= 60)` took **58.4 s** (the service's own ceiling is 60 s) and
`>= 10` never returned. The cost is in scanning every painting's sitelink count,
which a narrower range does not avoid. Binding the count instead of filtering it
turns the scan into a lookup — `VALUES ?sitelinks { 20 21 22 }` answered in 11 s
and `{ 60 … 99 }` in 8.5 s — so the walk asks for a few crowded low counts at a
time and the whole sparse top of the range in one request.

Paged that way, **12 requests, 0 failures**, paintings (`P31 Q3305213`) with a
Commons image (`P18`):

| sitelinks ≥ | paintings |
|---:|---:|
| 60 | 5 |
| 45 | 24 |
| 30 | **106** |
| 25 | 169 |
| 20 | 325 |
| 18 | 434 |
| 16 | 569 |
| 15 | 666 |
| 14 | 787 |
| 12 | 1,103 |
| 10 | **1,575** |

≥ 30 reproduces the 16:46 audit's 108 (106 here — the graph moved), which is why
30 is too high: 106 paintings is not a corpus. **The chosen threshold is 10**, the
floor of the measured walk, giving **1,575 paintings**. Ten Wikipedia editions is
a real bar — most paintings have none — and the lower the threshold, the more
abstract nouns reach a depiction at all: `love` (Q316) is depicted by 4 of these
paintings and `family` (Q8436) by 13, and both of those are lost at 20.

The smoke test passes: **Q12418 (Mona Lisa) is in the set**, at 146 sitelinks, the
highest count in it.

### The gate that was not met

manifest holds **1,644**, and the ceiling was never 2,299:

- the `isHighlight` id list is **2,290** objects, not 2,310 or 2,299 — those

  the parameter 2a measured as not filtering;
- of the 2,247 this session hydrated, **603 (26.8%) are not public domain**, and
  a highlight that is not public domain has no image to show;
- so the whole highlight set can yield about **1,675** public-domain objects, and
  1,644 of them are in the manifest. 2,000 was not reachable from highlights.

The corpus as a whole is 3,212 artworks, and the remaining 43 unhydrated ids can
be picked up by a later pass without re-fetching anything.

## Two faults found by seeding, not by testing

1. **`entities.preferred_label` is `varchar(255)`** and the seeder clamped titles
   to 300 characters, so the run died on the first Met highlight with a long
   title (*"Rebel Cassion Destroyed by Federal Shells. At Fredericksburgh, May 3,
   1863. Eight Horses Killed."* is one of the shorter long ones). Clamped to the
   column's own width, with a test. **The Phase 2a provider has the same 300 in
   `Met.title/1`** (`met.ex`), and a discovery result with a title that long
   would take the same path into `create_work` and fail the run the same way. It
   is untouched here because 2a is out of this phase's bounds; it is a real
   latent crash and wants a one-line fix in whatever phase owns that file.

2. **Only Wikidata rows carry a sitelink count**, so a single ranking over the
   merged catalog handed every one of the section's twelve slots to Wikidata and
   the Met's 1,644 objects never reached a word page at all. Measured, then
   fixed twice over: the catalog query ranks within each source with a window,
   and the section interleaves the sources. `/define/ox` now reads Bonheur, a Met
   cabinet, Rembrandt, a Met Dürer, Van Gogh.
